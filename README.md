### 접근 제어 규칙

- '라우트 가드'를 구현하다 든 고민
    - 현재 수준의 서비스에서는 라우트 가드 로직이 단순하다
        - 'auth'가 필요한 페이지에 'guest'가 방문하면 '로그인 페이지'로 redirect
        - 'auth'가 없어야 하는 페이지에 '인증된' 유저가 방문하면 '메인 페이지'로 redirect
    - 만약 서비스 규모가 거대해진다면?
        - 똑같이 'auth'가 필요한 페이지라도, redirect 시킬 페이지를 다르게 하고 싶다면? (혹은 유저별로)
        - 'OO'가 필요한 페이지 -> OO가 다양해진다면? 성별/나이/유저레벨/가입일자 등등
        - 동일한 조건의 유저들이라도, 페이지 권한을 유저별로 다르게 하고 싶다면?
    - 권한의 레벨을 다르게 부여해서 접근을 조절하면 될 것 같은데, 단순 계층 구조면 꼬이는 부분이 무조건 발생할 것 같다
    - 당연하게도 역사적으로 오래된 고민이었고, 접근을 제어하는 대표적인 모델이 3가지 정도 있었다
- 대표적인 접근 제어 모델링 방식
    - RBAC: Role-based Access Control
        - 어떤 자원에 어떤 행동이 가능한지를 역할별로 정의하고, 유저에게는 역할을 부여
        - 역할간 계층을 만들어 높은 계층이 낮은 계층 역할을 상속받을 수도 있고, 한 유저가 여러 역할을 가질 수 있다
        - 조직 구성이 단순한 사내 시스템에서는 유효하지만, google drive같이 복잡한 소유 구조를 구현하기에는 부족
    - ABAC: Attribute-based Access Control
        - “모든 것을 제어한다” : 각 속성별 행위자, 행동, 자원을 i/then 구문으로 모두 분기처리
        - 높은 수준의 제어를 보장하고 세분화된 규칙을 세울 수 있다
        - 하지만 규칙 정의와 수정에 많은 시간 소요
    - ReBAC: Relation-based Access Control
        - 자원과 유저 사이에 어떤 관계가 있는지로 접근 제어 (node tree 느낌)
        - 유저가 어떤 자원 A를 소유하면, A에게 소유권이 있는 다른 자원들에도 접근할 수 있는 것
        - 구글은 이 모델로, 여러 서비스의 권한을 글로벌 스케일에서 p95 10ms이하로 제어한다고 한다
- 본 프로젝트에 적용해 본다면?
    - 굳이 적용하자면 ABAC가 적합하다고 생각
        - 유저 계층이 다양한 것도 아니고, 자원이 많지 않기 때문
    - guard 조건, 실패시 action을 자원(route)별로 정의해보았다
         - 라우트별로 세세하게 규칙을 정할 수 있다
         - 만약 유사한 guard check 로직을 타는 라우트가 많아질 경우 그룹으로 묶어서 처리할 수 있다

```jsx
export const routes = {
  [pathname.profile]: {
    render: ProfilePage,
    guard: () => !!state.loggedInUser,
    redirect: pathname.login,
  },
  [pathname.login]: {
    render: LoginPage,
    guard: () => !state.loggedInUser,
    redirect: pathname.main,
  }, ...
};
```

### Router: Browser vs Hash

- 이번 과제의 가장 핵심적인 기능 중 하나가 Routing이었다.
    - react에서 routing을 사용할 때, Browser router와 Hash router를 지정할 수 있었던 것이 생각났다.
    - 둘의 차이를 잘 몰랐던 나는, 왜 Hash Router를 사용하는지 이해할 수 없었다.
    - pathname으로 경로 분기하고, history.~~ 사용해서 navigate하면 되는 것 아닌가? 굳이 예쁘지도 않은 새로운 라우팅 방식을 사용하는 이유가 뭐지? 싶었다.
    - 그렇게 이번 과제를 구현하고 배포해보니, 두 방식의 차이와, 나눠서 사용할 수 밖에 없었던 이유에 대해 알 수 있었다.
- 두 방식 비교
    - Hash Router
        - 주소창에 #/path 형태로 라우팅됨. 실제 URL은 변하지 않는다.
        - location.hash를 감시해서 라우팅 처리
        - 서버에는 전혀 요청이 가지 않기 때문에, 서버 측 라우팅 설정 없이도 잘 동작 → 이게 가장 큰 차이점인것 같다.
        - 새로고침해도 서버 404가 발생하지 않음
        - 하지만 URL이 #/로 시작해서 깔끔하지 않고, SEO에 불리함
    - Browser Router (history api 기반)
        - 주소창에 실제 경로를 사용: http://a.com/profile
        - history.pushState()로 경로를 변경하고, popstate 이벤트로 뒤로가기 등을 감지
        - URL이 진짜처럼 보이므로 UX 측면에서 자연스러움. 깔끔함
        - 서버 설정이 필요함 (e.g. Vercel, Netlify에서 rewrite 설정 등)
        - 새로고침 시 서버에 해당 경로로 요청이 가기 때문에, 정적 호스팅 환경에서는 404가 발생할 수 있음
- 처음에 Browser Router로 배포했을때, 잘 동작하는 것 같았는데 새로고침하니까 404가 떴다.
    - index부터 시작해서 사용하면서 url이 변경된거랑, 처음부터 접속하는거랑 뭐가 다르지? 싶었다.
    - 생각해보니까, 정적 페이지 배포는 폴더 구조랑 비슷한 거더라.
    - 우리가 배포한 파일은 index.html 하나기 때문에, 이것만 요청할 수 있다. 다른 url로 접속하면 찾을 수 없는것.
- 그에 반해 Hash Router는 아무 설정 없이도 한 번에 잘 작동했다.
    - GitHub Pages는 서버 설정이 불가능한데, 이런 환경에서는 Hash Router가 거의 유일한 선택지였다. (새로고침까지 고려하면)
    - Browser/Hash Router는 단순히 문법이나 API의 차이가 아니라, 라우팅 전략과 배포 환경 전반을 고려해야 하는 아키텍처적 선택지였던 것이다. 클라이언트 뿐만 아니라 서버도 고려를 해야한다.. OMG
- 오 근데 다른 분들이 하신 방법을 참고하니, 404.html을 활용하여 현재 path를 index부터 다시 route시키는 눈속임(?)이 가능했다.
    - 이것도 삽질중..

### 컴포넌트 조합 가능한 구조에 대한 고민

- 본 과제의 초기 구현 버전에서는 4개의 페이지를 각각 html 문자열로부터 렌더링했다 (브라우저가 알아서)
- 페이지 내용이 많아지고, 공통된 부분이 보이기 시작하면 자연스럽게 컴포넌트로 분리하고 싶어짐
    - 컴포넌트 또한 초기에는 html 문자열로 작성하고, 부모 문자열 내 삽입
         - ```
           const Nav = `<nav> <ul> <li>1</li> <li>2</li> </ul> </nav>`
           const MainPage = `<main> ${Nav} </main>`
           ```
        - web api들을 사용하지 않는다면, 이 구조는 문제가 없다
        - 컴포넌트를 가장 작은 단위로 쪼개놓고, 단순 문자열 조합하여 렌더링하면 된다
        - 근데 그런 경우는 실제 사용시 거의 없음. 대부분 동적인 콘텐츠이기 때문
    - 동적인 콘텐츠로 만들기 위해서는 innerHTML에 html string을 넣고, 그 node를 hydrate(핸들러 부착 등) 과정이 필수
        - 컴포넌트로 쪼갠다 함은 곧, 컴포넌트의 html 문자열 템플릿과 hydrate할 범위를 한 파일로 작게 분리하는 것이 된다
    - 근데 이렇게 분리한 컴포넌트를 부모의 html 문자열에 넣는 순간 모든게 망가지기 시작한다
        - 브라우저는 부모의 문자열에 컴포넌트가 포함되었는지 여부를 알 수 없다.
        - 합쳐진 하나의 문자열을 통으로 다시 렌더링할 뿐
        - 그래서 자식이 hydrate 되었더라도, 문자열로 합쳐지고 다시 렌더링되는 과정에서, 이전에 부착된 핸들러들은 모두 초기화됨..
    - 그러면 어떻게 해야하나?
        - 자식의 hydrate 로직을 부모가 대신 해주면 된다
            1. 부모의 하위 요소들의 html 템플릿을 합쳐서 통으로 렌더링
            2. 하위 요소들의 hydrate 로직을 모두 불러와서, 최상위 부모 요소에서 일괄 실행
        - 근데 이러면 결국 최상위 페이지가 신경써야할 내용이 전혀 분산되지 않은 꼴이 된다
            - 각 요소의 hydrate 함수와 html 문자열만 별도 파일로 분리한 것일 뿐..

```jsx
export const NavComponent = {
    template: ()=>`<nav/>`
    onMount: ()=>{}
}
    
export const MainPage = {
    template: ()=> `<header> ${Nav.template()} </header>`
    onMount: ()=>{Nav.onMount()}
 }
```

- 그래서 일단 위와 같은 구조로 변경해보았음
    - 모든 페이지, 컴포넌트는 template, onMount 로 구성
        - 상위 컴포넌트의 template 내에 하위 컴포넌트의 template를 호출해서 삽입
        - 상위 컴포넌트의 onMount 내에 하위 컴포넌트의 onMount 호출
- 코드가 엄청 깔끔해졌다!
    - 이렇게 트리 구조를 만들면, hydrate 로직이 최상위 컴포넌트에 집중되지 않는다.
        - 최상위부터 최하위 컴포넌트까지 onMount가 연쇄적으로 호출된다
    - 부모의 template 내 원하는 위치에 자식 컴포넌트 template을 호출하고, 부모의 onMount에 자식 onMount를 추가하면 된다
- 물론 아직 단점도 있다
    - 요소의 고유성을 보장할 수 없다
        - querySelector(”nav”)와 같은 코드는, DOM 내 위치한 다른 컴포넌트의 요소를 건드릴 가능성이 있다
        - 이를 방지하려면 요소에 id를 넣어줘야하고, 겹치지 않게 관리해야 하는데 이 또한 overload
    - template, onMount를 각각 호출해줘야 한다
        - 컴포넌트를 렌더하고 싶으면, template, onMount를 쪼개서 호출해야 함..
        - onMount가 noop이어도 일단 호출하는게 구조상 일관성을 지킬 수 있는 길인데, 메모리 낭비로 이어질 수도 있다
- createElement 함수를 직접 호출하지 않고, 문자열로 렌더링하는 방식에서는 현재 구조가 (내 생각에는) 최선인 것 같기도 하다..
    - node를 직접 생성하고 수정하는 방식은 다음 과제에서 깊게 파헤쳐보도록 하자

### 반복되는 문자열을 상수로 분리

- 초기에는 HTML 요소의 id, name, localStorage의 key, 라우팅 path 등을 코드 곳곳에 직접 문자열로 하드코딩해서 사용했다
  - 로그인 폼에서는 <form id="login-form">처럼 문자열을 직접 작성
  - localStorage에 데이터를 저장하거나 가져올 때도 "users", "user" 같은 key를 직접 사용
-  이 방식은 처음에는 빠르게 개발할 수 있다는 장점이 있지만, 프로젝트가 커질수록 다음과 같은 문제가 발생 가능함
    - 동일한 문자열이 여러 파일에 반복되어 관리가 어렵다
    - 미묘한 오타("login-form"과 "loginform")를 찾기가 어렵다
    - 문자열이 일부 수정되면, 사용한 모든 위치를 찾아 직접 다 수정해야함. 누락되기 쉽다
    - Editor 자동완성 기능을 사용하지 못한다
- 이러한 문제를 해결하기 위해, 자주 사용되는 문자열을 한 곳에서 관리할 수 있는 CONST 상수 객체로 정리했다.
    
```jsx
export const CONST = {
  lsKey: {
    users: "users",
    user: "user",
  },
  loginForm: {
    formId: "login-form",
    field: {
      username: "username",
      password: "password",
    },
  },
  profileForm: {
    formId: "profile-form",
    field: {
      username: "username",
      email: "email",
      bio: "bio",
    },
  },
 pathname: {
    main: "/",
    login: "/login",
    profile: "/profile",
  },
};
```
    
- 폼 생성 시에는 다음과 같이 사용
    
```jsx
<form id="${CONST.profileForm.formId}">
  <input id="${CONST.profileForm.field.username}" name="${CONST.profileForm.field.username}" />
</form>
```
    
- 라우팅 설정에도 경로 상수를 사용
    
```jsx
export const routes = {
  [CONST.pathname.profile]: {
    render: ProfilePage,
    guard: () => !!state.loggedInUser,
    redirect: CONST.pathname.login,
  },
};
```

- 이렇게 관리했더니, 아주 깔끔해졌다!
  - 수정할 문자열이 있으면 상수 파일에서 한 번만 변경하면 된다.
  - IDE에서 상수 객체를 인식해 자동완성 사용 가능
  - 코드 작성 속도와 가독성 향상

    - 대규모 서비스 관점에서 상수나 route guard 로직을 고민해보고 관리하는 경험
- 아직도 잘 모르겠는 것
    - 일단 과제는 잘 깔끔하게 마무리 한 것 같은데, Q&A 세션이랑 다른 분들 작업내용 참고하니 아직 갈길이 멀었다.

    - state도 일반 객체 말고 좀더 흐름을 파악하기 쉬운 구조로 관리해야 할 것 같다 (구독 관리 포함)
    - 또 hydrate 과정에서 발생하는 DOM 노드 중복 선택이나, 이벤트 핸들러 중복 부착 문제를 해결하기 위한 방법도 더 고민해봐야 할 것 같다. 실행 순서를 보장할 수 있는..?
- 실무에 적용해본다면
    - 현재 업무에서는 react, vue를 사용하고 있기 때문에 DOM 렌더링이랑 이벤트 부착같은 로직은 당연히 vanilla로 구현하는 것보다 훨씬 더 많이 최적화되어있다고 생각한다.
    - 자원 접근 권한 관리에 대해 고민한 경험은, 나중에 대규모 서비스를 설계할때 잘 활용할 수 있을 것 같다.
        - 서비스의 성격, 유저 계층에 따라 다를 것 같다.
